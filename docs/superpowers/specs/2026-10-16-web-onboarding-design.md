# ta-web first-install onboarding in the browser

**Status:** design approved in conversation, spec awaiting review
**Date:** 2026-10-16
**Builds on:** `2026-10-10-web-app-port-design.md` (the port spec). Auth stays invite-only
after the first account; tenancy, the commit boundary and the jobs model are unchanged.

## 1. Purpose

A homelab operator should be able to write a two-line `.env`, run `docker compose up -d`,
and do everything else in the browser. Today a first install also needs
`python -m tools.seed_admin`, `python -m tools.import_tadb`, a mounted `edict2` file with
`TA_EDICT_PATH`, and env edits for the Ollama / LibreTranslate defaults and the private-URL
flags. Adding a second user needs a raw `POST /invites`, because the SPA has no invite UI.

Target deployment: one machine on a home network, reached through Cloudflare Tunnel or
Tailscale. Not a goal: safe unattended exposure to the internet before the first account
exists (§3.4).

Success means:

- With a fresh database, any page redirects to a setup wizard that creates the first admin
  and signs them in.
- An admin can, from the browser: set server-wide MT/WordPress/syosetu settings, create and
  revoke invites, download or upload the EDICT2 dictionary, upload the Conjugations file.
- Any user can import a desktop `ta.db` into their own account from the browser, with a
  dry-run report before anything is written.
- The README's deployment section needs no shell command beyond writing `.env` and
  `docker compose up -d`.
- Existing env-configured installs keep working unchanged.

## 2. What stays in env

| Stays env-only | Why |
|---|---|
| `TA_SECRET_KEY` | Encrypts stored credentials; must exist before any DB access. Compose keeps `:?` (required). README gives the generation one-liner. |
| `TA_DATABASE_URL` | Needed to reach the DB at all. |
| `TA_SITE_ADDRESS`, ports | Caddy needs them before any page loads. |
| `TA_COOKIE_SECURE`, `TA_SESSION_TTL_DAYS`, login limits, `TA_RUN_JOBS_WORKER` | Security- or boot-sensitive. |
| `TA_DATA_DIR` (new) | Where dictionary files and uploads live. Default `./data`; compose sets `/data`. |

Everything in §4 moves to the browser, with env kept as a fallback.

## 3. First-run setup wizard

### 3.1 API (`api/routers/setup.py`, unauthenticated)

- `GET /setup/status` → `{"needs_setup": bool}`; true while the `users` table is empty.
- `POST /setup/admin {email, password}`:
  - takes `pg_advisory_xact_lock(<fixed key>)`, then re-counts users inside the lock;
  - any user exists → `409`;
  - otherwise creates the admin with `create_admin()` (moved from `tools/seed_admin.py`
    to `api/accounts.py`; same 12-character minimum, same default profile) and starts a
    session exactly as `/auth/login` does (shared helper, same cookie);
  - `201` with `UserOut`.
- Two concurrent claims: the lock serialises them, exactly one gets `201`, the other `409`.
- `tools/seed_admin.py` stays as a thin CLI over `create_admin()` (recovery path); the
  README no longer lists it in the deployment steps.

### 3.2 SPA

- New `/setup` route outside `RequireAuth`.
- On boot the app fetches `/setup/status`. While `needs_setup` is true, every route
  (including `/login` and `/invite`) redirects to `/setup`. The redirect away from `/setup`
  is decided once, when the wizard mounts: if `needs_setup` is already false then, it sends
  the visitor to `/login` (or `/` when signed in). After step 1 succeeds the mounted wizard
  keeps running its remaining steps even though `needs_setup` is now false.
- Steps; only step 1 is mandatory, steps 2–4 have **Skip** and are reachable later from the
  Admin page (§4–5) or the Import page (§6):
  1. **Create admin:** email, password, repeat password.
  2. **Server settings:** the §4 form, with the hint "Ollama or LibreTranslate on this
     machine or your network? Turn on *Allow private addresses*."
  3. **Dictionary:** the §5 download button and upload control.
  4. **Import desktop library:** the §6 upload card.
  5. **Done:** link to the library.
- Wizard progress after step 1 is client state only; reloading mid-wizard lands on the
  library, which is fine because every later step lives elsewhere too.

### 3.3 Admin link

Shell nav shows **Admin** only when `me.is_admin`.

### 3.4 Exposure warning

The wizard is open to whoever reaches it first. The README tells the operator to open the
site on the local network and create the admin **before** enabling Cloudflare Tunnel.
Tailscale-only access is safe as-is. No setup token: chosen deliberately for simplicity.

## 4. Server settings

### 4.1 Storage

New model `ServerSetting` (`server_settings`): `key` text PK, `value` JSONB,
`updated_at`, `updated_by` (FK users, `SET NULL`). Registered in `api/models/__init__.py`;
autogenerated migration.

### 4.2 Keys and validation

| Key | Type | Validation | Env fallback |
|---|---|---|---|
| `ollama_url` | str | empty or http/https URL | `TA_OLLAMA_URL` |
| `libretranslate_url` | str | empty or http/https URL | `TA_LIBRETRANSLATE_URL` |
| `mt_allow_private_urls` | bool | | `TA_MT_ALLOW_PRIVATE_URLS` |
| `wp_allow_private_urls` | bool | | `TA_WP_ALLOW_PRIVATE_URLS` |
| `syosetu_delay_seconds` | float | 1–60 | `TA_SYOSETU_DELAY_SECONDS` |

Unknown keys → `404`. Invalid values → `422`. Admin-set URLs are operator-trusted, like the
env defaults, so they are not passed through `check_user_url`.

### 4.3 Lookup

`api/server_settings.py` exposes `effective(db) -> ServerPrefs` (a frozen dataclass of the
five keys). Value = DB row if present, else `get_settings()` field. One query per call, no
cache. Callers switch from `get_settings().<key>` to it:

- `api/routers/mt.py` `_configure` (both URLs, `mt_allow_private_urls`)
- `api/publish.py` (`wp_allow_private_urls`)
- `api/fetch_job.py` and `api/routers/scrape.py` (`syosetu_delay_seconds`)

### 4.4 API (`api/routers/admin.py`, every route `require_admin`)

- `GET /admin/settings` → list of `{key, value, source: "db" | "env" | "default"}`.
  `env` means the env var is set; `default` means neither row nor env var.
- `PUT /admin/settings/{key} {value}` → upsert, returns the entry.
- `DELETE /admin/settings/{key}` → delete row, idempotent `204` (key-store rule).

### 4.5 Invites

Existing `POST /invites`, `GET /invites` unchanged. New `DELETE /invites/{id}`: deletes an
unused invite, `404` if missing, `409` if already used. Invites are server-wide admin
objects, so any admin may revoke any invite.

### 4.6 SPA (`/admin`)

Three tabs:

- **Server:** the §4.2 form; each field shows a source badge ("from env" / "default") and
  a **Reset** button when the source is `db`. Shared with wizard step 2.
- **Invites:** create (optional email, TTL days) → shows a copyable
  `${location.origin}/invite?token=…` link once; list with status pending / used / expired;
  **Revoke** for pending ones.
- **Dictionary:** §5.

Non-admins visiting `/admin` see "Admin only" (API answers 403).

### 4.7 Deferred

User list, promote/demote admin, disable account. Roles stay a single `is_admin` boolean;
RBAC is not introduced (no shared data exists for finer roles to gate).

## 5. Dictionary files

### 5.1 Location and resolution

Files live at `<TA_DATA_DIR>/dict/edict2` and `<TA_DATA_DIR>/dict/conjugations.txt`.
`api/dictionary.py` resolves each path:

1. `TA_EDICT_PATH` / `TA_CONJUGATIONS_PATH` if set (env wins, existing installs unchanged);
2. else the data-dir file if it exists;
3. else none.

`jparser._edict_path` / `_conj_path` call the resolver. The `lru_cache`d loaders key on
`(path, mtime_ns)` so a replaced file is picked up without restart.

The JParser `NeedsSetup` message becomes: "JParser needs the EDICT2 dictionary. An admin
can download it from Admin → Dictionary."

### 5.2 Download (admin)

- `POST /admin/dictionary/edict/download` → queues job `dict_download`; `409` while one is
  active server-wide.
- Handler (`api/dict_job.py`) fetches the hardcoded
  `https://www.edrdg.org/pub/Nihongo/edict2.gz` with an injected `httpx.Client`
  (`http_client` seam, as in `api/publish_job.py`), `follow_redirects=False`, streaming.
- Decompresses with a 128 MiB output cap (over → job error), writes
  `edict2.tmp` in the dict dir, validates (≥1000 entries parse with
  `jparser._parse_edict_line`), then `os.replace` into place. Failure leaves the old file.
- Progress via the existing job events.

### 5.3 Upload (admin)

- `POST /admin/dictionary/edict` (multipart): plain or gzip (detected by magic bytes),
  same cap and validation as §5.2.
- `POST /admin/dictionary/conjugations` (multipart): validated by loading it with
  `jparser._load_conj_rules`; must yield at least one rule.
- Both: 64 MiB upload cap, written via temp file + `os.replace`.
- Caddy: `/api/admin/dictionary/*` gets a 64 MiB `request_body` limit (EPUB pattern).

### 5.4 Status and removal

- `GET /admin/dictionary` → per file `{present, source: "env" | "data_dir" | null, size,
  updated_at, entries}` (`entries` = loaded index size for edict, rule count for
  conjugations; `null` when absent).
- `DELETE /admin/dictionary/{edict|conjugations}` removes the data-dir file, idempotent
  `204`. An env-pointed file is shown read-only with no remove button.

The Dictionary tab credits EDRDG (CC BY-SA 4.0) next to the download button; so does the
README.

## 6. Desktop `ta.db` import

### 6.1 Code move

The logic of `tools/import_tadb.py` (620 lines) moves to `api/core/tadb_import.py` (row
mapping and schema checks) and `api/core/tadb_run.py` (`import_tadb`, fingerprints, report),
each under ~400 lines. `tools/import_tadb.py` becomes a thin CLI; its tests keep passing
unchanged apart from import paths.

### 6.2 Flow

Any signed-in user, into their own account.

1. `POST /import/tadb` (multipart `file`): streamed to
   `<TA_DATA_DIR>/uploads/<user_id>/<uuid>.db`, 1 GiB cap. The first 16 bytes must be
   `SQLite format 3\0`, else `422` and the file is deleted. Queues a `tadb_import` job with
   `dry_run=True`. Returns `{upload_id, job_id}`. `409` while the user has an active
   `tadb_import` job.
2. The SPA follows the job's events and shows the dry-run report from its result: per-table
   written / skipped / already-present counts, messages, and any refusal (already imported,
   account not empty) as text.
3. `POST /import/tadb/{upload_id}/run {force: bool}` queues the real job. **Import** sends
   `force=false`; **Import anyway** (`force=true`) is offered only when the dry run reported
   a refusal. `404` for an unknown upload or another user's.
4. `DELETE /import/tadb/{upload_id}` discards the upload, idempotent `204`.

### 6.3 Cleanup

The upload file is deleted when the real job finishes (success, failure or cancel). The
job-worker startup sweep also deletes upload files older than 24 h.

### 6.4 Job

Handler `tadb_import` in `api/tadb_job.py` calls `import_tadb(ctx.db, path, user_id,
dry_run=…, force=…)` and stores the report in the job result. The import already runs inside
one SAVEPOINT, so an interrupted or failed real run writes nothing and can be retried. The
source is opened `mode=ro`, as today.

### 6.5 Caddy

`/api/import/tadb` gets a 1 GiB `request_body` limit.

### 6.6 SPA

A **Desktop library (ta.db)** card on `/import`, reused as wizard step 4.

## 7. Compose and README

### 7.1 `docker-compose.yml`

- `api`: `TA_DATA_DIR: /data`, volume `ta_data:/data`.
- `caddy`: `ports: ["${TA_HTTP_PORT:-80}:80", "${TA_HTTPS_PORT:-443}:443"]`.
- `TA_SECRET_KEY` stays required.

### 7.2 README: new "Deploy (homelab)" section

1. Create `.env` with `TA_SECRET_KEY` (generation one-liner) and `TA_SITE_ADDRESS`.
2. Address mode:
   - **Cloudflare Tunnel or `tailscale serve`:** `TA_SITE_ADDRESS=:80` (plain http inside;
     the tunnel terminates TLS). Point the tunnel at `http://<host>:<TA_HTTP_PORT>`.
   - **Tailscale direct / LAN:** `TA_SITE_ADDRESS=<machine>.<tailnet>.ts.net` or the LAN
     address.
3. Set `TA_HTTP_PORT` / `TA_HTTPS_PORT` if 80/443 are taken.
4. `docker compose up -d`.
5. **Open the site on your network and create the admin account before enabling
   Cloudflare Tunnel.** Until then, anyone who reaches the site can become admin.
6. Follow the wizard.
7. Backups: the `pgdata` and `ta_data` volumes, plus `TA_SECRET_KEY` (without it, saved API
   keys cannot be decrypted; everything else survives).

The existing developer quick start keeps `seed_admin` and `import_tadb` as CLI alternatives.
The MT section points at Admin → Server / Dictionary, with env vars as fallbacks.

### 7.3 Known limitation (not fixed here)

Behind Cloudflare Tunnel every request reaches Caddy from `cloudflared`, so the per-address
login limiter is effectively global: repeated failures lock everyone out for the window.
Recorded in the carry-over memory; the later fix is an opt-in trust of `CF-Connecting-IP`.

## 8. Testing

**pytest**

- Setup: `needs_setup` true then false; claim creates admin + session cookie; second claim
  `409`; two concurrent claims (two connections) → exactly one `201`; short password `422`.
- Server settings: precedence db > env > default and the `source` field; reset falls back;
  invalid values `422`; unknown key `404`; non-admin `403`; MT `_configure`, publish and
  syosetu fetch read the effective values.
- Invites: revoke pending `204`, used `409`, missing `404`.
- Dictionary: download job via `httpx.MockTransport` (good gz, oversize gz → error and old
  file kept, garbage → error, redirect → error); upload plain and gz; conjugations
  validation; resolver precedence; loader reloads after mtime change; second download `409`.
- ta.db: upload non-SQLite `422`; upload → dry-run job report; run → rows written and file
  deleted; refusal then `force`; other user's `upload_id` `404`; sweep deletes old files;
  second active job `409`.

**Playwright**

- Admin page: change a setting and reset it, create and revoke an invite, upload a tiny
  edict fixture.
- Wizard steps 2–5 and the `/import` ta.db card with a small fixture database.
- Step 1 needs an empty database, which the shared `ta_e2e` run cannot provide; it is covered
  by the pytest API tests only.
