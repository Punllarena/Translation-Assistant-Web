# Admin branding (brand name, logo, favicon)

## Intent

The app is heading toward a public reader (comments, EPUB downloads). The operator needs to make the site their own.
This first slice covers only the **brand name, logo and favicon**, inside the site itself. Reader look and feel,
EPUB/WordPress credits and other branding are later work.

## Goals

- An admin sets, in Settings → Admin → **Branding** (new page in the Admin group, admin-only like its siblings):
  - **Brand name** (text).
  - **Logo** (image upload) and an **optional dark-mode logo** (second upload). Light mode, or dark mode with no dark
    logo, uses the one logo.
  - **Show name next to logo** (checkbox, the admin's choice: a logo that already contains the name can stand alone).
  - **Favicon** (separate image upload).
  - Save and **Reset to default**.
- Where it shows: the header brand (`Shell.tsx`), login, accept-invite and setup pages (they use the same
  `.brand` markup today), and the browser tab title and favicon (`web/index.html`).
- Header cases: logo + name; logo only (name hidden); no logo (today's look: the 訳 mark followed by the name).
- **Defaults** (nothing configured): name "Translation Assistant", header shows the 訳 mark, and the favicon is that
  same 訳 mark (there is no favicon today). The 訳 mark is kept as the default logo and doubles as the default favicon.
- Changes show right after saving, with no rebuild.

## Non-goals / anti-goals

- No branding of EPUB exports, WordPress posts or the future reader's theme/layout/colours.
- No per-user branding; it is one server-wide setting.
- Must not break the pre-login pages: branding must load for signed-out visitors, and a failed or slow branding
  request must fall back to the defaults, never a blank or broken header.
- An uploaded file must never be able to run script in the site's origin (see SVG below).

## Constraints / codebase facts

- Server-wide admin settings live as rows in `server_settings` (`api/models/server.py`, read via
  `api.server_settings`); admin-only routes follow the existing `/admin/settings` pattern. Binary uploads need
  their own storage (a table like `volume_covers`, or files under `TA_DATA_DIR`); the **backup/restore** feature
  exports every table in `Base.metadata`, so a new table is covered automatically but must be checked, and files
  outside the database would need adding to the backup, so prefer a table.
- All routers are built with `api_router()`; handlers `flush()` only. Migrations are autogenerated.
- Pre-login pages need a public endpoint for name, "show name" flag and image URLs, like the public `/setup/status`.
  It must also answer during maintenance as sensible (maintenance already 503s everything but `/healthz` and
  `/restore/status`; the SPA falls back to defaults).
- Image routes must be public (an `<img>` and a favicon `<link>` cannot send credentials selectively on the login page),
  cacheable for good by using a new row id on every replace (the covers pattern: `GET /covers/{id}`).
- Tokens only for colour in CSS (`web/src/styles/`); no literal colours. Header logo needs a sensible max height
  and width so a wide logo cannot break the header; dark theme is `:root[data-theme="dark"]`.
- Size discipline: no Python module over ~400 lines.

## Decisions made with the user

- Logo and favicon are two separate uploads.
- Name beside logo is an admin checkbox.
- Optional dark-mode logo.
- Scope: in-site only for now. Keep the 訳 mark as the default and use it as the default favicon.

## Calls made by the author (not yet confirmed by the user)

- Accepted types: PNG, WebP, SVG, ICO for the favicon; PNG, WebP, SVG for logos (no JPEG/GIF). Size cap about
  1 MiB per file. Type is sniffed from the bytes, not trusted from the filename or content type.
- SVG safety: serve images with `Content-Security-Policy: sandbox` (or `default-src 'none'`) and
  `X-Content-Type-Options: nosniff`, and render them only through `<img>`/`<link>`, never inline. Rejecting SVGs that
  contain `<script>` or event handlers is optional extra on top of that.
- Name: 1–60 characters after trimming; blank means the default name.
- The "show name" checkbox defaults on and only matters when a logo exists.
- Uploaded logo is not used as the favicon automatically; with no favicon uploaded, the default 訳 favicon shows.
- The tab title is the brand name only.

- Storage: the name and show-name flag live in their own small table next to the image rows, not in `server_settings`
  (whose keys feed the admin settings list). The public branding endpoint is *not* added to `MAINTENANCE_ALLOWED`;
  the SPA falls back to defaults during maintenance.
- Size cap enforced both in Caddy and in the API, as other uploads are (streamed read that stops at the cap).
  Sniff each format (PNG/WebP magic bytes, ICO signature, SVG by `<svg` text) and serve the sniffed type.
- Dark logo shown by toggling two `<img>` tags on `data-theme` (not `prefers-color-scheme`, since theme can be set by hand).
- Cache the last-seen branding in `localStorage` (like `ta.theme`) to avoid a flash of the default name; Reset clears it.
- The default 訳 favicon is a static SVG in a new `web/public`; make sure the Dockerfile/Caddy serve it.
- Tests: a failed branding fetch still renders login/setup; backup/restore round-trip includes the image table (bytea).
