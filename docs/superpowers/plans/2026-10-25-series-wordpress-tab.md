# Series WordPress Tab and Series Summary Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move a series' WordPress fields into a new WordPress tab with a Series summary field that replaces the desktop's chapter 0, sent as chapter index 0 with the next chapter published.

**Architecture:** Three new `series` columns hold the summary and its send state. A pure module turns text into publish lines and back. An app module sends a pending summary through the existing `wp_http.publish` just before a chapter goes out, in the single, batch and Illustrations paths. One Alembic revision adds the columns and moves published chapter-0 documents into them. The ta.db importer does the same on import. The SPA gets a fifth tab, and both Settings and WordPress are restyled into `.panel` sections.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic, Postgres, pytest; React + TanStack Query, vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-series-wordpress-tab-design.md`

## Global Constraints

- Handlers only `flush()`; no new commit points (CLAUDE.md commit boundary). The summary state rides the chapter's transaction.
- Series fetched via `scoped()`; another user's series is 404.
- Migration columns come from `alembic revision --autogenerate`; the data step is added by hand to that same revision's `upgrade()` (data steps are not autogenerated).
- No Python module over ~400 lines.
- Stylesheets use tokens only, never literal colours; reuse `.panel`, `.panel.pad`, `.panel-head`, `.field`, `.row-fields`, `.hint` (`web/src/styles/controls.css`, `settings.css`).
- WordPress error text shown to the user is only the plugin's message (`WPPublishError.message`); any other failure is the fixed string `"sending the series summary failed"`.
- Run `npm run gen:api` after the API schema change; commit `web/src/api/schema.d.ts`.
- Exact copy:
  - guard message `SUMMARY_MOVED = "The series summary is published from the series' WordPress tab, not as a chapter."`
  - summary chapter title `"Summary"`

## Review Focus

1. **Summary with Windows line endings or trailing spaces:** `\r\n\r\n` must split paragraphs like `\n\n`, and a whitespace-only paragraph is dropped. Test in Task 2.
2. **Batch spanning two series, both with pending summaries:** each series' summary is sent once, before its own first chapter. Test in Task 3.
3. **Chapter in a series whose summary is pending but the chapter build fails (no translated lines):** the summary must not be sent, because the chapter never went. Test in Task 3 (single route: `build_chapter` runs before `send`).
4. **A re-imported ta.db** must not overwrite a summary the user has since edited. Test in Task 5.
5. **The migration on a series whose summary document sits inside a volume, ahead of live chapters:** the renumber happens, and the mismatch is logged rather than crashing. Test in Task 4.

### Task 2: Summary text ↔ publish lines (pure)

**Files:**
- Create: `api/core/wp_summary.py`
- Test: `tests/test_core_wp_summary.py`

**Interfaces:**
- Produces:
  - `summary_lines(text: str) -> list[dict]`: one `{"prefix": "%", "translated_text": paragraph}` per paragraph. Paragraphs are split on one or more blank lines, after normalising `\r\n` to `\n`. Single newlines inside a paragraph become a space. Each paragraph is stripped, and empty ones are dropped.
  - `lines_to_summary(lines: list[dict]) -> str`: the inverse used by the migration and the importer. It groups `$` continuation lines exactly as `build_chapter_body` does (`api/core/wp.py:35`), joining with a space, drops blank groups, and joins the groups with `"\n\n"`.

**Interfaces:**
- Consumes: `summary_lines` (Task 2); `Series.wp_summary*` (Task 1); `publish.series_meta`, `wp.build_payload`, `wp_http.publish`.
- Produces: `wp_summary.send(c: httpx.Client, series: Series, endpoint: str, key: str) -> None`. It never raises. It returns at once unless `series.wp_summary_pending` is set and `series.wp_summary.strip()` is non-empty. Otherwise it posts `build_payload(doc_meta={"series_title": series.title, "series_order": 0, "chapter_title": "Summary", "volume_title": ""}, series_meta=publish.series_meta(series), lines=summary_lines(series.wp_summary), api_key=key, attribution=False)`. On any returned result it sets pending False and error `""`. On `WPPublishError` it sets error `exc.message`; on any other exception it calls `log.exception` and sets error `"sending the series summary failed"`. Pending stays True on failure.
- Produces: `publish.SUMMARY_MOVED` (exact copy in Global Constraints). `build_chapter` raises `NotReady(SUMMARY_MOVED)` when `chapter_number(db, doc) == 0` or `doc.wp_chapter_index == 0`, checked right after the `is_illustrations` check.

### Task 4: Migration data step — published chapter 0 becomes the summary

**Files:**
- Modify: `migrations/versions/<rev>_series_wp_summary.py` (from Task 1)
- Test: `tests/test_migration_series_summary.py` (load the revision with `importlib` as `tests/test_migration_series_glossary.py` does)

**Interfaces:**
- Consumes: `lines_to_summary` (Task 2).
- Produces: `move_summaries(conn) -> list[str]` in the revision module, called from `upgrade()` after the column adds. It returns its log lines, and `upgrade()` writes each one to `logging.getLogger("alembic.runtime.migration")`. The algorithm, in SQL over `conn`, runs in this order:
  1. **Live summary documents.** For each series that has documents with `wp_chapter_index = 0 AND wp_status IN ('publish','future')`, take the lowest id. Set the series' `wp_summary` to `lines_to_summary` of that document's lines (ordered by `line_number`), with `wp_summary_pending = false`. Delete every such document in the series; lines and images cascade. Log a line when there was more than one.
  2. **Unsent ones.** Set `wp_chapter_index = NULL` on the remaining documents with `wp_chapter_index = 0`.
  3. **Renumber.** For each affected series whose `syosetu_url = ''`, renumber `series_order` to `row_number() OVER (ORDER BY series_order, id)`.
  4. **Mismatch report.** In the affected series, log every document with a live `wp_status` whose display number differs from its non-NULL `wp_chapter_index`. The display number is `series_order` minus the number of `is_illustrations` documents before it; a syosetu series uses `series_order` as is. Skip `is_illustrations` documents themselves.
- The `downgrade()` docstring says the deleted documents are not restored.
