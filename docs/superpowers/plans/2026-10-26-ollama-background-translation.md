# Ollama Background Translation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ollama translates queued chapters in labelled paragraph chunks during a user's scheduled window, saves
suggestions with reasoning and stats, and the SPA shows them in the editor, a Jobs page and a Statistics tab.

**Architecture:** Pure rules (presets, chunk cutting, prompt, answer check, outcome scoring, schedule windows,
streamed-JSON scanning) live in a new `api/ollama/` package with unit tests. DB work (`work.py`, `store.py`) is
synchronous SQLAlchemy run in the threadpool; Ollama HTTP is async `httpx`. A separate Ollama runner and a
scheduler tick start in the lifespan next to `jobs.worker`; a per-user in-process lane serialises every request to a
user's server, by-hand first. The SPA gets an Ollama card + Reasoning dialog, a `/jobs` page, an Ollama Statistics
tab, Ollama settings, and queue/flush actions on the Volumes tab.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic, Postgres, httpx, pytest; React, TanStack Query, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-26-ollama-background-translation-design.md`

## Global Constraints

- Every router is built with `api_router()`; handlers only `flush()`, never `commit()`.
- User-owned rows are fetched with `scoped()` (404, never 403). List endpoints filter by `user_id` inline.
- New models are imported in `api/models/__init__.py`; migrations are autogenerated (`alembic revision
  --autogenerate`), data steps added to the generated file.
- No Python module over ~400 lines.
- Ollama calls take an injected `httpx.AsyncClient`; tests use `httpx.MockTransport`, never a live server.
- Sanctioned commits outside the route boundary after this work: `/mt/stream`'s `_put_sync`, the job worker, the
  Ollama runner (`api/ollama/runner.py`), the by-hand stream's save (`api/routers/ollama_editor.py`) and the
  scheduler tick (`api/ollama/schedule.py`). `CLAUDE.md` lists them.
- Presets (verbatim): Small CPU (≈2B) 12 lines + 5 context; Medium (4–8B) 25 + 10; Large / GPU whole chapter + 0;
  Custom.
- Retention: 3 months after the newest `translated_at` of a fully translated chapter.
- `check_user_url` always refuses `169.254.0.0/16`, `fe80::/10`, `0.0.0.0`, `::` and `metadata.google.internal`,
  even with `allow_private`.
- Copy: "Set an Ollama URL under Settings → Machine translation." / "This model didn't reason." / "Translating lines
  {a}–{b}…" / "Waiting for the night run's current chunk…" / "Reroll lines {a}–{b}" / "source changed".
- Tests: `pytest` against `ta_test`; one pytest run at a time; `TA_DATABASE_URL` set to `127.0.0.1` (localhost hangs
  on this machine).

## Review Focus

1. **A chapter edited while a run is mid-chunk** (a line translated by hand, or Edit Source) — the save must not
   overwrite a translated line's state or attach a suggestion to a line whose `raw_text` changed. Test in Task 9
   (`test_save_skips_lines_changed_since_plan`).
2. **Ollama returns HTTP 200 then a truncated stream or a non-JSON answer** — the chunk must fall to halving, never
   save partial lines. Test in Task 10 (`test_truncated_stream_counts_as_failed_answer`).
3. **A window that crosses midnight and a DST change** — 23:00–06:00 in `Europe/London` on the last Sunday of
   October must open once and close at local 06:00. Test in Task 12 (`test_window_across_midnight_and_dst`).
4. **The queue points at deleted things** (a series, volume or chapter deleted after queuing) — the run skips and
   drops the item rather than failing. Test in Task 9 (`test_next_chunk_drops_items_whose_target_is_gone`).
5. **Two browser tabs on the same chapter both start the by-hand chunk** — the second waits in the lane and, when its
   turn comes, finds the lines answered and returns the saved results without a new request. Test in Task 14
   (`test_second_by_hand_request_reuses_saved_results`).

### Task 3: Chunk cutting

**Files:**
- Create: `api/ollama/chunks.py`
- Test: `tests/test_ollama_chunks.py`

**Interfaces:**
- Produces:
  - `@dataclass(frozen=True) class Item: line_number: int; prefix: str; text: str; known: str | None = None` — `text`
    is display text; `known` is a translation or a current suggestion (context inside a chunk); `known is None`
    means the line is asked.
  - `paragraphs(items: Sequence[Item]) -> list[list[Item]]` — drops items whose `text` is empty; a new paragraph
    starts at every `%` item (a `$` item with no `%` before it starts one too).
  - `cut(items: Sequence[Item], chunk_lines: int) -> list[list[Item]]` — whole paragraphs, filled while the total
    stays ≤ `chunk_lines`; a paragraph longer than `chunk_lines` is its own chunk; `chunk_lines == 0` → one chunk.

  - `context_before(items: Sequence[Item], first_line: int, n: int) -> list[Item]` — the last `n` non-empty items
    before `first_line`.
  - `@dataclass class RequestStats: first_line: int; last_line: int; asked: int; ok: bool; clamped: bool; depth: int;
    reasoning: str; prompt: str; prompt_tokens: int | None = None; output_tokens: int | None = None;
    prompt_ms: int | None = None; eval_ms: int | None = None; load_ms: int | None = None;
    total_ms: int | None = None; first_token_ms: int | None = None` — one Ollama request's record, filled by Task 10
    and saved by Task 9 (`prompt` is the JSON of the messages). Lives here so the pure and DB modules share it.

### Task 4: Prompt, context size and answer check

**Files:**
- Create: `api/ollama/prompt.py`, `api/ollama/answer.py`
- Test: `tests/test_ollama_prompt.py`, `tests/test_ollama_answer.py`

**Interfaces:**
- Consumes: `Item` (Task 3).
- Produces (`prompt.py`):
  - `FORMAT_SCHEMA: dict` — `{"type":"object","properties":{"lines":{"type":"array","items":{"type":"object",
    "properties":{"id":{"type":"integer"},"text":{"type":"string"}},"required":["id","text"]}}},"required":["lines"]}`
  - `FORMAT_RULES: str` — app-owned instructions appended to the user's system prompt: labels are line numbers;
    lines under "Context" and lines marked `(done)` are not to be translated or returned; return every asked id once,
    in order; a line marked `$` may be `""` when its meaning went into the line before.
  - `build_messages(system_prompt: str, src: str, dst: str, before: list[Item], chunk: list[Item]) -> list[dict]` —
    system = user prompt with `{src}`/`{dst}` replaced + `"\n\n" + FORMAT_RULES`; user = `"Context:\n"` + before as
    `[n] text => known` lines (omitted when empty), then `"Translate:\n"` + chunk lines as `[n]$ text` / `[n] text`,
    with ` (done) => known` on known items.
  - `estimate_tokens(text: str) -> int` — ASCII chars / 4 + non-ASCII chars, rounded up.
  - `num_ctx(messages: list[dict], asked: int) -> int` — prompt estimate + 60 per asked line + 512, rounded up to a
    multiple of 1024, minimum 2048.
- Produces (`answer.py`):
  - `class AnswerError(ValueError)`
  - `check(answer: str, asked: list[Item]) -> dict[int, str]` — parse JSON; every asked id exactly once, in asked
    order, no other ids; `""` only for `$` items; texts stripped. Raises `AnswerError` with a short reason.
  - `halves(items: list[Item]) -> tuple[list[Item], list[Item]]` — split at the `%` item nearest the middle (not the
    first item); with none, split at `len // 2`. Precondition `len(items) >= 2`.

### Task 5: Outcome scoring and the streamed-JSON scanner

**Files:**
- Create: `api/ollama/outcome.py`, `api/ollama/json_lines.py`
- Test: `tests/test_ollama_outcome.py`, `tests/test_ollama_json_lines.py`

**Interfaces:**
- Produces:
  - `outcome.score(suggestion: str, final: str) -> tuple[str, float]` — normalise both (casefold, strip
    punctuation per `unicodedata` category `P*`, collapse whitespace); equal → `("used", 1.0)`; else
    `difflib.SequenceMatcher` ratio `r`; `r >= EDITED_MIN` (0.5) → `("edited", r)`, else `("ignored", r)`.

    of the `lines` array as soon as its closing `}` arrives; objects missing either field are skipped.
    Algorithm: track in-string / escape state and brace depth over the concatenated text; record the start offset
    when depth goes 1→2; on 2→1 `json.loads` that slice.
